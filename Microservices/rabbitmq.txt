Q1. What is RabbitMQ and why did you use it in your project?
--------------------------------------------------------------
ANSWER:
RabbitMQ is a message broker. It allows different services/modules to
communicate with each other asynchronously without calling each other directly.

For ex., we have an Order Service. Whenever an order will placed, we needed to send a confirmation email and SMS. 
Instead of calling the customer/
Email Service directly using REST (synchronous call), we can publish message to RabbitMQ. 
The Email Service consumed that message independently. So even if the Email Service was down, the order was
not affected, and the email would be sent once the service will back up."

WHY THIS IS GOOD TO SAY:
- Shows you understand decoupling
- Shows real use case, not just theory


Q2. Why not just call the other service directly using REST API?
--------------------------------------------------------------
Direct REST calls create tight coupling between services.
Order Service --> Payment Service --> Email Service (all synchronous)

If Email Service is down, the whole chain can fail or the order API
becomes slow (waiting on Email Service response).

With RabbitMQ: Order Service --> RabbitMQ --> Email Service

Order Service just publishes the message and returns success immediately. 
Email Service picks it up whenever it is available. This is called ASYNCHRONOUS COMMUNICATION.


Q3. Explain the main components of RabbitMQ.
--------------------------------------------------------------
1. Producer - The service that sends the message.
   Example: Order Service publishing "order placed" event.

2. Consumer - The service that receives and processes the message.
   Example: Email Service listening and sending confirmation mail.

3. Queue - Temporary storage where messages wait until consumed.
   Like a waiting line (FIFO in general).

4. Exchange - The router. Producer never sends message directly to
   the queue; it always sends to an Exchange, which decides which
   queue(s) the message should go to.

5. Binding - The rule/link that connects an Exchange to a Queue
   (using a routing key).

FLOW:
Producer -> Exchange -> (via Binding) -> Queue -> Consumer


Q4. What are the types of Exchanges in RabbitMQ? (Most Important)
--------------------------------------------------------------
1. DIRECT EXCHANGE
   Routes message using EXACT routing key match.
   Example: routing key "order.created" goes only to "OrderQueue".
   Use case: Sending order confirmation only to Order Queue.

2. FANOUT EXCHANGE
   Sends the same message to ALL queues bound to it, ignoring routing key.
   Example: When order is placed, notify Email, SMS, and Analytics
   service all at once - broadcast.

3. TOPIC EXCHANGE (Most asked in interviews)
   Uses pattern matching on routing key.
   Example routing keys: order.created, order.updated, payment.failed
   A queue can subscribe using patterns like:
     order.*   -> matches order.created, order.updated (one word after order.)
     payment.# -> matches payment.failed, payment.failed.retry (zero or more words)
   
4. HEADERS EXCHANGE (Rarely asked, mention briefly)
   Routes based on message headers instead of routing key.
   Rarely used in real projects, good enough to just mention it exists.


Q5. What happens if the consumer crashes while processing a message?
   (Message Acknowledgement)
--------------------------------------------------------------
RabbitMQ uses ACK (Acknowledgement) to make sure no message is lost.

Flow:
1. Consumer receives the message.
2. Consumer processes it (e.g., sends email).
3. Consumer sends ACK back to RabbitMQ.
4. Only after ACK, RabbitMQ deletes the message from the queue.

If the consumer crashes BEFORE sending ACK, RabbitMQ assumes the
message was not processed and re-delivers it to another consumer
(or the same one once it's back).
JAVA EXAMPLE (Spring Boot with manual ACK):

    @RabbitListener(queues = "emailQueue", ackMode = "MANUAL")
    public void consumeMessage(Message message, Channel channel) throws IOException {
        try {
            // process message - send email
            emailService.send(message);

            // manually acknowledge
            channel.basicAck(message.getMessageProperties().getDeliveryTag(), false);
        } catch (Exception e) {
            // reject and requeue or send to DLQ
            channel.basicNack(message.getMessageProperties().getDeliveryTag(), false, true);
        }
    }


Q6. What happens if the RabbitMQ server restarts? Will messages be lost?
   (Message Durability)
--------------------------------------------------------------
By default, if RabbitMQ restarts, all queues and messages are lost
(since they are stored in memory).
To prevent this, we make:
1. Queue durable = true  (queue definition survives restart)
2. Message persistent = true (delivery mode = PERSISTENT)

JAVA EXAMPLE:
    @Bean
    public Queue emailQueue() {
        return new Queue("emailQueue", true); // true = durable
    }

    // While sending message, mark it persistent
    rabbitTemplate.convertAndSend("emailQueue", message, m -> {
        m.getMessageProperties().setDeliveryMode(MessageDeliveryMode.PERSISTENT);
        return m;
    });

NOTE TO MENTION: "Durable queue alone is not enough - the message
itself also needs to be marked persistent, otherwise it can still
be lost on restart."


Q7. What is Prefetch Count? How did you use it for load balancing?
--------------------------------------------------------------
When multiple consumer instances are running (e.g., 3 pods of Email
Service), RabbitMQ distributes messages among them.

Prefetch count defines how many unacknowledged messages a single consumer can hold at a time.

Example: If prefetch count = 1, RabbitMQ gives one message to a
consumer, waits for ACK, then sends the next one. This ensures fair
distribution and avoids one consumer instance getting overloaded
while others sit idle.

JAVA EXAMPLE (application.yml):
    spring:
      rabbitmq:
        listener:
          simple:
            prefetch: 1

We had 3 instances of our email consumer. We set prefetch count to 1 so RabbitMQ would only send the next message once
the previous one was acknowledged, ensuring even load distribution across all instances.


Q8. What is a Dead Letter Queue (DLQ)? How did you use it?
--------------------------------------------------------------
When a message repeatedly fails processing (e.g., payment service
keeps failing 5 times), instead of retrying forever, RabbitMQ moves it
to a Dead Letter Queue (DLQ).
Use cases:
- Debugging failed messages later
- Manual reprocessing
- Avoiding infinite retry loop that blocks the main queue

JAVA EXAMPLE (declaring queue with DLQ config):
    @Bean
    public Queue emailQueue() {
        return QueueBuilder.durable("emailQueue")
                .withArgument("x-dead-letter-exchange", "dlx.exchange")
                .withArgument("x-dead-letter-routing-key", "dlx.routingkey")
                .build();
    }

WHAT TO SAY: "In our project, if an email failed to send after 3
retries, the message was automatically routed to a Dead Letter Queue.
We had a small dashboard/alert to check DLQ messages and reprocess
them manually after fixing the issue."


Q9. RabbitMQ vs Kafka - what's the difference?
--------------------------------------------------------------
SIMPLE ANSWER FOR INTERVIEW:
RabbitMQ  -> Best for task processing / job queues where each message
             needs to be processed once (e.g., send email, process order)
Kafka     -> Best for event streaming, big data, and cases where the
             same event needs to be read by many consumers and replayed
             later (e.g., analytics, log aggregation)

One-liner to say: "RabbitMQ is a traditional message broker good for
transactional/task-based messaging, while Kafka is a distributed
event streaming platform good for high-throughput analytics use cases."


Q10. RabbitMQ vs REST API - difference?
--------------------------------------------------------------
Feature          REST                          RabbitMQ
--------------------------------------------------------------------
Communication    Synchronous                   Asynchronous
Dependency       Both services must be online  Services can be offline
Speed            Slower under heavy load       Better for background tasks
Reliability      Less (no retry by default)    High (ACK, retry, DLQ)

Q11. (IMPORTANT - REAL SCENARIO) How do you avoid DUPLICATE emails
     or notifications being sent via RabbitMQ?
====================================================================
RabbitMQ guarantees at-least-once delivery, which means duplicate messages are possible if a consumer crashes 
after processing but before acknowledging. To handle this in our notification service, we attached a unique message ID
to every event at the producer side. On the consumer side, before sending the actual email, we checked in
database whether that message ID was already processed. If it was already there, we simply
skipped sending and just acknowledged the message. This made our email consumer idempotent, so even if RabbitMQ redelivered 
a message, the user would never receive a duplicate email.

WHY DUPLICATES HAPPEN:
RabbitMQ (like most message brokers) guarantees "AT LEAST ONCE"
delivery, not "EXACTLY ONCE". Duplicate messages can happen because:
1. Consumer processed the message (sent email) but crashed/network
   dropped BEFORE sending ACK back to RabbitMQ.
2. RabbitMQ, not knowing it was processed, redelivers the same
   message to another consumer.
3. Producer itself retries publishing (e.g., due to a timeout) and
   accidentally publishes the same event twice.

Result: Same email/notification is sent 2 times to the user.

HOW TO SOLVE IT (explain these points in interview):

1. IDEMPOTENCY USING A UNIQUE MESSAGE ID (Most important, always mention this)
   - Every message carries a unique ID (e.g., orderId + eventType,
     or a UUID generated at producer side).
   - Before processing, the consumer checks if this ID was already
     processed (using Redis or a DB table) - if yes, skip it.

   JAVA EXAMPLE (using Redis as a fast idempotency check):
       @RabbitListener(queues = "emailQueue")
       public void consumeMessage(EmailEvent event) {
           String key = "email:sent:" + event.getMessageId();

           // atomic check-and-set, expires after 24 hours
           Boolean isNew = redisTemplate.opsForValue()
                   .setIfAbsent(key, "1", Duration.ofHours(24));

           if (Boolean.FALSE.equals(isNew)) {
               log.info("Duplicate message ignored: {}", event.getMessageId());
               return; // already processed, skip
           }

           emailService.send(event);
       }

   WHY REDIS setIfAbsent works well: it is atomic, so even if two
   consumer threads pick up the same message id at the same time
   (race condition), only one of them succeeds in sending it.

2. IDEMPOTENCY USING DATABASE (if Redis not available)
   - Maintain a table like `processed_messages(message_id PRIMARY KEY,
     processed_at)`.
   - Before sending email, try to INSERT the message_id.
   - If insert fails due to PRIMARY KEY / unique constraint violation
     -> it means it's a duplicate -> skip sending.
   - This is reliable because DB unique constraint enforces it even
     under concurrent access.

3. USE MANUAL ACK CORRECTLY (avoid ack-before-processing mistake)
   - Never use "auto ack" for critical operations like sending email.
   - Send ACK only AFTER the email is successfully sent, so RabbitMQ
     doesn't prematurely think it's processed - but this alone does
     NOT fully prevent duplicates (it actually causes them if the ACK
     itself fails after email is sent), which is exactly why point 1
     (idempotency check) is still needed on top of manual ack.

4. PRODUCER SIDE - AVOID DUPLICATE PUBLISH
   - Use "Publisher Confirms" in RabbitMQ so producer knows for sure
     the message reached the broker before considering it "sent".
   - Generate the unique message ID at the point of the business
     event (e.g., when order is created), not at the time of publish,
     so even if producer retries publishing, the ID stays the same
     and consumer-side idempotency check still catches it.

BONUS - QUICK ONE-LINERS FOR RAPID FIRE ROUND
====================================================================
Q: Is RabbitMQ push-based or pull-based?
A: Push-based - RabbitMQ pushes messages to the consumer.

Q: Can one queue have multiple consumers?
A: Yes, and RabbitMQ round-robins messages among them (competing
   consumers pattern) - useful for scaling.

Q: What is a Routing Key?
A: A label attached to a message used by the Exchange to decide which
   queue(s) to deliver it to.

Q: Does RabbitMQ guarantee message order?
A: Yes, within a single queue with a single consumer, order is
   preserved. With multiple consumers on the same queue, order is not
   guaranteed.

Q: What Spring library did you use for RabbitMQ?
A: spring-boot-starter-amqp, using RabbitTemplate to publish and
   @RabbitListener to consume.
